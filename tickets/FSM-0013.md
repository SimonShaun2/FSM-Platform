## Objective
Build the GitHub execution infrastructure — milestones, labels and project views — so ticket
state lives in the repository rather than in conversation.

## Product context
Master directive §56 requires GitHub-based execution, and §59 requires cross-team
communication through repository artifacts rather than chat memory. Prior work tracked status
in chat and in ad-hoc markdown, which is precisely how the repository ended up with three
mutually contradictory accounts of project state.

## User story
As any team member, I need to see what is ready, blocked, in review and done without asking
anyone, so dependencies unlock work automatically rather than through coordination overhead.

## Scope
GitHub milestones, labels, project board and views, issue templates, PR template.

## Deliverables
1. **Milestones** — one per sprint, Sprint 0 through Sprint 22, each describing its scope
   from `SPRINT_ROADMAP.md`.
2. **Labels**, grouped and colour-coded:
   - *Priority:* `P0`, `P1`, `P2`, `P3`
   - *Domain:* `domain:crm`, `domain:scheduling`, `domain:dispatch`, `domain:jobs`,
     `domain:estimates`, `domain:invoices`, `domain:payments`, `domain:memberships`,
     `domain:communications`, `domain:booking`, `domain:portal`, `domain:inventory`,
     `domain:workforce`, `domain:reporting`, `domain:marketing`, `domain:ai`,
     `domain:integrations`, `domain:industry-packs`, `domain:platform`
   - *Owner role:* `owner:TL-01`, `owner:FE-01`, `owner:FE-02`, `owner:BE-01`, `owner:BE-02`,
     `owner:FS-01`, `owner:FS-02`, `owner:DES-01`, `owner:DES-02`, `owner:QA-01`,
     `owner:QA-02`, `owner:QA-03`, `owner:DO-01`, `owner:DO-02`
   - *Function:* `frontend`, `backend`, `fullstack`, `design`, `devops`, `qa`
   - *Risk:* `risk:payments`, `risk:security`, `risk:data`, `risk:tenant-isolation`, `risk:breaking-change`
   - *Type:* `mobile`, `ai`, `integration`, `migration`, `adr`
   - *Status:* `status:blocked`, `status:ready`, `status:in-progress`, `status:design-review`,
     `status:peer-review`, `status:qa`, `status:ready-to-merge`
3. **Project views**: Backlog · Ready · In Progress · Design Review · Peer Review · QA ·
   Blocked · Ready to Merge · Done · Release Candidate.
4. **Issue template** implementing the full ticket standard from master directive §54 — all
   required fields present, none optional.
5. **PR template** requiring: ticket reference, self-review checklist confirmation, shared
   contract change declaration with consumers, test evidence, observability additions, peer
   reviewer, QA owner.
6. **Sprint 0 issues created** — FSM-0001 through FSM-0014, correctly labelled, milestoned and
   dependency-linked.
7. `GITHUB_WORKFLOW.md` finalised with the automated progression procedure.

## Acceptance criteria
- [ ] All 23 sprint milestones created with scope descriptions
- [ ] Every label above created, grouped and colour-coded consistently
- [ ] All 10 project views configured with correct filters
- [ ] Issue template contains every field from master directive §54
- [ ] PR template requires shared contract declaration
- [ ] All 14 Sprint 0 issues created with correct labels, milestone and dependency links
- [ ] Blocked issues visibly show what blocks them
- [ ] `status:ready` accurately reflects dependency state on creation

## Required tests
Manual verification that each view filters correctly, checked against a deliberately mislabelled test issue.

## Impact
**API / Database / Frontend / Mobile / Integration:** none.

## Security considerations
Repository is public. Confirm no issue, template or label description exposes credentials,
customer data or unremediated security findings. FSM-0009 findings must not be filed as
public issues until remediated — track privately and reference by identifier only.

## Tenant isolation considerations
None.

## Observability requirements
Project board state is the visible record of execution. Automated progression must keep it
accurate without manual curation.

## Migration requirements
None.

## Rollback considerations
Labels and milestones are additive and removable. No code impact.

## Non-goals
Not creating issues beyond Sprint 0. Not automating progression — that is Sprint 1 tooling.
Not migrating historical `TICKET-NNN` work into issues.

## Required review
DO-01 implements · Claude reviews label taxonomy and the issue template against §54.

## Required QA
QA-01 verifies every view filters correctly and every Sprint 0 issue is correctly classified.

## Completion procedure
Merge → all Sprint 0 work tracked on the board from this point → update `PROJECT_STATE.md` §5.
