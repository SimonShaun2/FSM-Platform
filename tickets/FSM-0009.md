## Objective
Assess the security posture of the existing codebase with particular focus on tenant
isolation, and produce a risk-ranked remediation plan. This is an adversarial review, not a
checklist.

## Product context
The platform is multi-tenant and handles payment data, customer PII and property access
information including gate codes. V2 expands to Stripe Terminal, saved payment methods, a
customer portal and a public API — every one of which increases exposure. Tenant isolation
was a stated V1 principle but has never been adversarially tested. A stated principle and a
verified property are different things.

## User story
As the QA engineer owning security and data integrity, I need a verified picture of where
tenant isolation actually holds, so that V2 does not build new surfaces on an unsound
foundation.

## Scope
Authentication and token handling, authorisation and roles, tenant scoping across every
route and service, webhook verification, file upload handling, secrets management, input
validation, audit trails, and any finding escalated from FSM-0001, FSM-0003, FSM-0004,
FSM-0006, FSM-0007 or FSM-0008.

## Deliverables
1. `docs/audit/SECURITY-POSTURE.md` — full assessment with risk ranking.
2. **Tenant isolation matrix**: every route × tenant scoping enforced at service layer
   (verified by reading the query) × cross-tenant test present × verdict.
3. **Adversarial test results**: attempt actual cross-tenant access against a locally seeded
   two-tenant database, for every domain. Record what succeeded. A successful cross-tenant
   read or write is a P0 finding.
4. Authentication assessment: token generation, storage, expiry, refresh, revocation, session
   handling, MFA readiness. `refresh_tokens` receives particular scrutiny — it was absent
   from the schema file that engineers were briefed on.
5. Authorisation assessment: role model, permission enforcement point, any client-side
   authorisation decision.
6. Secrets management: hardcoded credentials, `process.env` outside `@fsm/config`, secrets in
   history, secrets in test fixtures, secrets in logs.
7. Webhook security: signature verification per endpoint, replay protection, idempotency.
8. File upload security: type validation, size limits, storage isolation, direct-access
   exposure, malware considerations.
9. Input validation coverage: routes without Zod validation.
10. Audit trail assessment: which sensitive actions are recorded and which are not.
11. Consolidated risk register: finding, severity, exploitability, affected surface, remediation, owning sprint.

## Acceptance criteria
- [ ] Every route present in the tenant isolation matrix with a verified verdict
- [ ] Adversarial cross-tenant testing actually executed against a two-tenant database, not reasoned about
- [ ] Every P0 finding has a written reproduction
- [ ] Authentication assessment covers the full token lifecycle including revocation
- [ ] No hardcoded credential remains anywhere in the working tree
- [ ] Every webhook endpoint's signature verification status verified by reading the handler
- [ ] File upload paths assessed end to end including direct storage access
- [ ] Every escalated finding from other Sprint 0 tickets incorporated
- [ ] Risk register ranked by exploitability × impact, each item assigned an owning sprint
- [ ] No remediation performed except credential rotation

## Required tests
Adversarial test suite written and committed: two seeded tenants, attempted cross-tenant read
and write against every domain. These tests are a permanent deliverable, not throwaway audit
scaffolding — they become the Sprint 2 tenant isolation regression suite.

## Impact
**API / Database / Frontend / Mobile:** assessment only.
**Integration:** any compromised credential is rotated immediately as part of this ticket.

## Security considerations
This ticket is the security deliverable. Findings are handled confidentially until remediated.
If a P0 is found in a currently deployed environment, escalate to TL-01 and the founder
immediately rather than proceeding with the audit.

## Tenant isolation considerations
The central concern. Every claim of tenant safety must be backed by a passing adversarial
test. An implementation that looks correct but has no test is recorded as unverified, not safe.

## Observability requirements
Assess whether a cross-tenant access attempt would currently be detectable in logs. If not,
that is a Sprint 1 observability requirement.

## Migration requirements
None.

## Rollback considerations
Credential rotation must be coordinated with DO-01 to avoid breaking running environments.

## Non-goals
Not remediating findings beyond credential rotation. Not implementing MFA. Not adding
missing validation. Sprint 1, Sprint 2 and Sprint 20 own remediation.

## Required review
QA-02 implements · TL-01 reviews all P0 and P1 findings · DO-02 reviews secrets management ·
founder informed of any P0 affecting a deployed environment.

## Required QA
QA-03 independently reproduces every P0 finding.

## Completion procedure
Merge → feed risk register into FSM-0012, Sprint 1, Sprint 2 and Sprint 20 → update
`PROJECT_STATE.md` §5 → the adversarial suite becomes a permanent CI gate under FSM-0010.
