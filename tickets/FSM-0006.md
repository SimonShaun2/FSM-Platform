## Objective
Inventory every background worker, queue, scheduled job, webhook handler and external
integration at the baseline, and classify each against V2 requirements.

## Product context
The baseline includes `apps/worker`, `apps/webhook`, `packages/jobs` and `packages/ai`, plus
integrations with Stripe, Twilio, SendGrid, OpenAI and Cloudflare R2. V2 significantly
expands async workload — communications, marketing automation, memberships, recurring
billing, AI recommendations. The existing queue topology and adapter boundaries must be
assessed for whether they can carry that load.

## User story
As the engineer who will own AI, automation and integrations, I need to know exactly what
async infrastructure exists and how sound it is, so Sprint 1 scopes the worker platform
correctly rather than discovering gaps mid-sprint.

## Scope
`apps/worker`, `apps/webhook`, `packages/jobs`, `packages/ai`, and all vendor adapter files.

## Deliverables
1. `docs/audit/WORKER-INVENTORY.md`: per queue — name, purpose, producers, consumers,
   payload shape, retry policy, idempotency status, failure handling, classification.
2. Processor inventory: per processor — file, queue, trigger, idempotency verified yes/no,
   error handling, observability, test coverage, classification.
3. Scheduled job inventory: cron jobs, schedules, and whether they are currently running.
4. Webhook inventory: per handler — source, events handled, signature verification status,
   idempotency status, classification.
5. Integration adapter inventory: per vendor — adapter file location, whether vendor calls
   are properly isolated to the adapter, SDK version, error handling, retry behaviour,
   credential handling, classification.
6. Adapter boundary violation register: every vendor call made outside its adapter file.
7. Async coverage gap: which V2 async requirements have no current infrastructure.

## Acceptance criteria
- [ ] Every queue inventoried and classified with rationale
- [ ] Every processor's idempotency verified by reading the code, not assumed
- [ ] Every webhook handler's signature verification status recorded as verified fact
- [ ] Every webhook handler's idempotency status recorded — a non-idempotent payment webhook is a P0 finding
- [ ] Every vendor adapter located; every out-of-adapter vendor call listed with file and line
- [ ] Scheduled jobs documented including whether they currently execute
- [ ] Async coverage gap complete against V2 sprint requirements
- [ ] Each REPLACE names its target sprint
- [ ] No worker or integration behaviour changed

## Required tests
None added. Existing worker tests run and results recorded for FSM-0007.

## Impact
**API:** none. **Database:** none. **Frontend:** none. **Mobile:** none.
**Integration:** full inventory; no live integration is invoked during this audit. Do not
call vendor APIs against production credentials while auditing.

## Security considerations
Webhook signature verification is a required field. Any unverified webhook endpoint is a P0
finding escalated to QA-02 immediately. Credential handling in every adapter is recorded —
any hardcoded credential or `process.env` access outside `@fsm/config` is escalated.

## Tenant isolation considerations
Every queue payload must carry tenant scope. A payload without it means a worker may operate
with ambiguous tenant context — a P0 finding.

## Observability requirements
Record current queue health monitoring, failed-job visibility, dead letter handling and
webhook delivery monitoring. Gaps feed Sprint 1 observability scope.

## Migration requirements
None.

## Rollback considerations
Documentation only.

## Non-goals
Not fixing idempotency. Not adding signature verification. Not restructuring queues. Not
upgrading SDKs. Findings only.

## Required review
FS-02 implements · BE-01 peer reviews · TL-01 approves the async coverage gap analysis as it
directly shapes Sprint 1.

## Required QA
QA-02 independently verifies webhook signature and idempotency findings, given these are the
highest-risk items in this inventory.

## Completion procedure
Merge → escalate P0 findings to FSM-0009 immediately → feed into FSM-0012 and Sprint 1 →
update `PROJECT_STATE.md` §5.
