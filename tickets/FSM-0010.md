## Objective
Assess current CI/CD, environments and deployment state, and design the tiered CI gate
strategy that Sprint 1 will implement.

## Product context
The repository has no evident CI configuration and history shows work merged directly to
`main` without automated verification. `docs/planning/PRODUCTION-DEPLOYMENT.md` describes a
Railway target. V2 requires intelligent tiered gates per master directive §58 — comprehensive
verification without running every expensive suite on every trivial commit.

## User story
As the DevOps engineer owning CI/CD, I need to know what exists and what each gate should
cost, so Sprint 1 builds a pipeline engineers will not route around.

## Scope
CI configuration, build scripts, Turborepo configuration, environment definitions, deployment
configuration, secrets management infrastructure, and the existing deployment guide.

## Deliverables
1. `docs/audit/CICD-STATE.md`: current CI configuration (or its absence), build pipeline,
   Turborepo task graph and cache effectiveness, deployment mechanism, environment inventory.
2. Build assessment: clean-clone install and build timing per workspace; failures recorded.
3. Environment inventory: what exists (local, staging, production), what is deployed, whether
   any environment is currently live and serving traffic.
4. Secrets management assessment: how secrets are currently supplied, where they live, rotation capability.
5. **Tiered CI gate design** for Sprint 1 — the primary deliverable:
   - *Tier 1, every commit:* format, lint, typecheck, unit tests, affected-package build. Target under 5 minutes.
   - *Tier 2, every PR:* integration tests, migration validation, tenant isolation suite, dependency audit, secret scanning, full build.
   - *Tier 3, pre-merge to main:* E2E, accessibility, performance checks, API contract tests.
   - *Tier 4, release:* full regression, security scan, artifact generation, release certification.
   Each gate specifies trigger, runtime budget, failure behaviour and owner.
6. Branch and merge strategy: protection rules, required checks, merge method, release branching.
7. Deployment readiness gap: what is missing before Sprint 22 can ship.
8. Rollback capability assessment.

## Acceptance criteria
- [ ] Current CI state documented as verified fact including confirming absence
- [ ] Clean-clone build executed and timed per workspace
- [ ] Every environment inventoried, including whether anything is currently live
- [ ] Tiered gate design covers all four tiers with runtime budgets and owners
- [ ] Every check in master directive §58 assigned to a tier or explicitly deferred with reason
- [ ] Tenant isolation suite from FSM-0009 assigned to Tier 2
- [ ] Governance terminology check from FSM-0002 assigned to Tier 1
- [ ] Branch protection and required checks specified
- [ ] Rollback capability assessed for each environment
- [ ] No CI implemented in this ticket

## Required tests
Clean-clone build verification, timed, three runs to establish variance.

## Impact
**API / Database / Frontend / Mobile:** none.
**Integration:** document which integrations require credentials in CI and how they will be
stubbed — CI must never call live vendor APIs.

## Security considerations
Secret scanning and dependency audit are required Tier 2 gates. Assess whether CI would have
any access to production credentials; it should not.

## Tenant isolation considerations
The adversarial suite from FSM-0009 becomes a blocking Tier 2 gate. Design accordingly.

## Observability requirements
Specify build and deployment monitoring, failure alerting and pipeline metrics for Sprint 1.

## Migration requirements
Migration validation is a required Tier 2 gate: migrations must replay cleanly from empty on
every PR touching the schema.

## Rollback considerations
Document current rollback capability honestly, including if there is none.

## Non-goals
Not implementing CI. Not configuring deployment. Not creating environments. Sprint 1 implements.

## Required review
DO-01 implements · DO-02 peer reviews · TL-01 approves the tiered gate design · QA-03
approves gate assignment since they own release certification.

## Required QA
QA-03 verifies the gate design covers every quality requirement in `QA_STRATEGY.md` scope and
that no critical check is unassigned.

## Completion procedure
Merge → feed gate design into Sprint 1 → update `PROJECT_STATE.md` §5 → coordinate with
FSM-0001 so branch protection required-checks are enabled once CI exists.
