## Objective
Establish the true test baseline — what exists, what passes, what it actually covers — and
classify the existing suite against V2 quality requirements.

## Product context
The baseline contains 42 test files. Prior project documentation claimed 234 passing tests
at Phase 1, but that figure has never been independently verified and predates roughly 20
further commits. Test counts reported in status documents are not evidence. V2 requires a
tiered CI strategy, so we need to know what we actually have before designing gates.

## User story
As the QA engineer who will own release certification, I need a measured, reproducible
picture of current test health, so that CI gates in Sprint 1 are set against real numbers
rather than aspirational ones.

## Scope
All `*.test.ts` and `*.test.tsx` files, test configuration, fixtures, factories, test
database setup, and any E2E configuration.

## Deliverables
1. `docs/audit/TEST-BASELINE.md`: total test files, total test cases, pass count, fail count,
   skipped count, total runtime — all from an actual run, output captured verbatim.
2. Per-domain coverage table: domain, service test present, route test present, line
   coverage %, branch coverage %.
3. Failing and skipped test register: every failure and skip with its reason.
4. Test quality assessment: tests asserting real behaviour versus tests asserting mocks;
   tests that would pass against a broken implementation.
5. Critical path coverage gap: which core workflows have no test at any level.
6. Tenant isolation test coverage: which domains have cross-tenant access tests. Absence is a
   finding for FSM-0009.
7. E2E status: whether Playwright is configured, whether any E2E test exists, whether it runs.
8. Test infrastructure assessment: database setup, fixtures, factories, determinism, flakiness.
9. Classification of the existing suite KEEP / REFACTOR / REPLACE / REMOVE.

## Acceptance criteria
- [ ] Test suite executed from a clean clone of the baseline; raw output committed
- [ ] Actual counts recorded — no figure carried over from prior documentation
- [ ] Coverage measured with a coverage tool, not estimated
- [ ] Every failing and skipped test has a documented reason
- [ ] Flaky tests identified by running the suite three times and comparing
- [ ] Critical path gap analysis complete against the lifecycle in `AGENTS.md` §1
- [ ] Tenant isolation test coverage recorded per domain
- [ ] E2E status recorded as verified fact
- [ ] Existing suite classified with rationale
- [ ] No test modified, fixed or added

## Required tests
This ticket runs tests; it does not write them. Three consecutive full runs are required to
identify flakiness.

## Impact
**API / Database / Frontend / Mobile / Integration:** none. If tests invoke external vendors,
record that as a finding — tests must not depend on live vendor calls.

## Security considerations
Flag any test containing real credentials, real customer data or production connection
strings. Escalate immediately to FSM-0009.

## Tenant isolation considerations
Cross-tenant access testing is a required column. A domain with no cross-tenant test cannot
be assumed tenant-safe regardless of what the implementation appears to do.

## Observability requirements
None.

## Migration requirements
Document whether tests require a migrated database and whether that setup is reproducible.

## Rollback considerations
Documentation only.

## Non-goals
Not fixing failing tests. Not raising coverage. Not writing E2E tests. Not de-flaking. All
remediation belongs to Sprint 1 and the sprint owning each domain.

## Required review
QA-01 implements · QA-03 reviews, since these numbers set the release gates they will own ·
TL-01 reviews the critical path gap analysis.

## Required QA
QA-03 independently reproduces the test run from a clean clone and confirms the numbers match.

## Completion procedure
Merge → feed into FSM-0010 CI gate design and FSM-0012 → escalate security findings to
FSM-0009 → update `PROJECT_STATE.md` §5.
