## Objective
Map the existing 38-table schema against the V2 target domain model, identify every gap, and
determine whether the existing model can be extended or must be restructured.

## Product context
Master directive §62 defines roughly 50 core entities the platform must ultimately support —
including Organization, Business Unit, Location, Project, Visit, Work Order, Inventory Item,
Warehouse, Vehicle Inventory, Purchase Order, Vendor, Commission, Timesheet, Referral and
Reward. The existing schema was designed for a deliberately narrower V1. The critical
question for the entire restart is whether V2 extends this schema or replaces it. Getting
this wrong costs multiple sprints.

## User story
As the Technical Lead, I need to know whether the existing data model is a foundation or a
constraint, so the rebaseline decision in FSM-0012 is made on evidence.

## Scope
The full entity list in master directive §62, mapped against the schema inventory from
FSM-0004.

## Deliverables
1. `docs/audit/DOMAIN-MODEL-GAP.md` — entity-by-entity mapping: target entity, existing table
   or none, coverage (full / partial / absent), gap description, owning sprint.
2. **Multi-tenancy model assessment** — the highest-risk item. The existing model appears to
   scope to a single company. V2 requires Organization → Business Unit → Location hierarchy
   and agency-style multi-company access. Determine whether the current tenant column can
   carry that or whether a hierarchical restructure is required. State the answer plainly.
3. Entity relationship gaps: required relationships the current model cannot express.
4. Extensibility assessment: custom fields, tags, industry pack configuration, feature
   modules — can the current model support these without structural change?
5. Naming and terminology reconciliation: where existing table names conflict with the V2
   domain vocabulary, and whether renaming is worth the migration cost.
6. **Restructure-versus-extend recommendation**, per domain, with reasoning and migration cost.
7. Migration risk assessment: which changes are additive, which are breaking, which require
   data migration.

## Acceptance criteria
- [ ] Every entity in master directive §62 mapped with a coverage verdict
- [ ] Multi-tenancy model assessment complete with an unambiguous recommendation
- [ ] Every gap assigned an owning sprint
- [ ] Extensibility assessment addresses custom fields, tags, industry packs and feature modules
- [ ] Restructure-versus-extend recommendation given per domain with reasoning
- [ ] Migration risk classified additive / breaking / data-migration-required
- [ ] Recommendation is decisive — "it depends" is not an acceptable outcome
- [ ] No schema changed

## Required tests
None. Conclusions requiring validation are prototyped in a scratch branch that is never merged.

## Impact
**API:** none now; the recommendation shapes every subsequent sprint's API surface.
**Database:** none now; this determines the Sprint 1 and Sprint 2 database strategy.
**Frontend / Mobile / Integration:** none now.

## Security considerations
The multi-tenancy assessment is a security deliverable as much as an architectural one. A
hierarchical tenant model changes every isolation guarantee. Coordinate directly with FSM-0009.

## Tenant isolation considerations
Central to this ticket. If the recommendation is a hierarchical restructure, the isolation
model must be redesigned in Sprint 2 and the FSM-0009 adversarial suite rewritten accordingly.

## Observability requirements
None.

## Migration requirements

## Rollback considerations

## Non-goals

produces the decision and its evidence.
