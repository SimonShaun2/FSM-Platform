## Objective
Inventory every table, column, relationship, index and constraint at the baseline; eliminate
the duplicate schema file; and classify each table against the V2 domain model.

## Product context
Two schema files exist. Root `fsm-schema.ts` holds 1,510 lines and 35 tables and is the file
handed to build sessions as context. The real schema at `packages/db/src/schema.ts` holds
1,644 lines and 38 tables. Three tables — `refresh_tokens`, `booking_settings`,
`booking_requests` — exist only in the real schema. Anyone briefed from the root file is
blind to authentication token storage and the entire booking domain. `booking_requests`
additionally carries the two-field SMS consent structure that has previously regressed.
See `PROJECT_STATE.md` BD-001.

## User story
As a backend engineer, I need exactly one schema file, so that what I am briefed on and what
the database actually contains can never diverge again.

## Scope
Both schema files, the migration directory, seed scripts, and every import path referencing
either schema.

## Deliverables
1. **`packages/db/src/schema.ts` established as the sole authoritative schema.** Root
   `fsm-schema.ts` deleted, not synchronised — a synchronised duplicate drifts again.
2. Every import updated to the canonical path. Zero references to the deleted file.
3. `docs/audit/SCHEMA-INVENTORY.md`: per table — name, purpose, column count, tenant scope
   column, soft-delete support, timestamps, foreign keys, indexes, owning domain,
   classification, rationale.
4. Full diff record of the three previously-missing tables, with their column definitions,
   documented so the drift is auditable.
5. `booking_requests` SMS consent fields documented explicitly by name, purpose and default
   value, with a regression note.
6. Migration inventory: every migration, applied status, whether it is reproducible from a
   clean database.
7. Index and constraint review: missing tenant-scope indexes, missing foreign key
   constraints, missing unique constraints.
8. Monetary column audit: every money column confirmed as decimal/string, never float.
9. If any build session context bundle references the root schema path, update it.

## Classification rubric
Per `docs/audit/BACKEND-INVENTORY.md` conventions — KEEP / REFACTOR / REPLACE / REMOVE, each
with a written rationale, each REPLACE naming its target sprint.

## Acceptance criteria
- [ ] Root `fsm-schema.ts` no longer exists
- [ ] `grep -r "fsm-schema"` across the repository returns zero operative hits
- [ ] All 38 tables inventoried and classified with rationale
- [ ] `refresh_tokens`, `booking_settings`, `booking_requests` fully documented
- [ ] `booking_requests` SMS consent fields named, defaults recorded, regression note written
- [ ] Every table's tenant scope column recorded; any table lacking one flagged to FSM-0009
- [ ] Every table's soft-delete support recorded; any lacking `deletedAt` flagged
- [ ] Migrations replay cleanly against an empty database
- [ ] Drizzle schema and actual migration output confirmed in sync
- [ ] Every monetary column confirmed non-float
- [ ] No schema behaviour changed — this is inventory plus deduplication only

## Required tests
Clean-database migration replay: empty Postgres → run all migrations → verify resulting
schema matches `packages/db/src/schema.ts` exactly. Existing test suite passes unchanged
after the deletion and import updates.

## Impact
**API:** import paths only; no contract change. **Database:** no structural change; file
consolidation only. **Frontend:** import paths if any reference the root file.
**Mobile:** none. **Integration:** none.

## Security considerations
Any table storing tokens, secrets or payment identifiers is listed separately with its
encryption-at-rest status for FSM-0009. `refresh_tokens` receives particular attention given
it was invisible to everyone working from the root file.

## Tenant isolation considerations
Tenant scope column presence is a required field for every table. A table without one is a
P0 security finding escalated to QA-02 immediately, not deferred to the consolidated report.

## Observability requirements
None.

## Migration requirements
No new migrations. If migrations are found not to replay cleanly, that is a finding for
FSM-0012 and a Sprint 1 remediation ticket — do not repair it here.

## Rollback considerations
Deletion of the duplicate is recoverable from git history. Import changes are mechanical
and revertible.

## Non-goals
Not designing the V2 schema — that is FSM-0011 and Sprint 1. Not adding tables, indexes or
constraints. Not fixing missing tenant scope. Findings only.

## Required review
BE-02 implements · TL-01 reviews classifications and the deduplication approach · BE-01
confirms no service breaks from the import change.

## Required QA
QA-02 verifies the clean-database replay, confirms zero remaining references to the deleted
file, and independently checks the three previously-missing tables are fully documented.

## Completion procedure
Merge → resolve BD-001 in `PROJECT_STATE.md` §3 → feed inventory into FSM-0011 and FSM-0012
→ update `PROJECT_STATE.md` §5 → notify all owners the canonical schema path has changed.
