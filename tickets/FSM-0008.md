## Objective
Inventory every dependency across the monorepo, identify vulnerabilities, licence risk and
staleness, and produce a prioritised remediation plan for Sprint 1.

## Product context
The codebase was last touched in May 2026. Dependencies have gone unmaintained for roughly
three months across a monorepo of four applications and five packages. Before building
significantly on this foundation we need to know what is vulnerable, what is abandoned and
what carries licence obligations incompatible with a commercial SaaS product.

## User story
As the DevOps engineer responsible for security operations, I need a complete dependency
picture, so that Sprint 1 upgrades are prioritised by risk rather than by convenience.

## Scope
Root `package.json`, all workspace `package.json` files, `pnpm-lock.yaml`, and transitive
dependencies.

## Deliverables
1. `docs/audit/DEPENDENCY-AUDIT.md`: full inventory — package, workspace, current version,
   latest version, versions behind, direct or transitive, licence.
2. Vulnerability register from `pnpm audit` plus a second independent scanner: package,
   severity, CVE, affected version, fixed version, exploitability in our usage context,
   remediation priority.
3. Licence compliance register, with anything copyleft or commercially restrictive flagged
   explicitly.
4. Staleness register: packages more than one major version behind, unmaintained packages,
   deprecated packages, packages with no release in 12+ months.
5. Framework currency assessment: Next.js, Fastify, Drizzle, BullMQ, and every vendor SDK —
   current version, latest, breaking changes between, upgrade effort estimate.
6. Prioritised remediation plan for Sprint 1: security fixes first, then breaking-change
   upgrades, then routine currency.
7. Duplicate and conflicting dependency versions across workspaces.

## Acceptance criteria
- [ ] Every direct dependency inventoried across all nine workspaces
- [ ] `pnpm audit` executed and raw output committed
- [ ] A second independent scanner used; results reconciled with the first
- [ ] Every critical and high vulnerability assessed for real exploitability in our usage, not just reported severity
- [ ] Every licence identified; no dependency left as "unknown"
- [ ] Framework currency assessed with upgrade effort estimates
- [ ] Remediation plan ordered by risk with each item sized
- [ ] Duplicate versions across workspaces identified
- [ ] No dependency upgraded in this ticket

## Required tests
None. If the audit reveals the lockfile does not resolve reproducibly, that is a P0 finding
for FSM-0010.

## Impact
**API / Database / Frontend / Mobile:** none.
**Integration:** vendor SDK versions recorded and cross-referenced with FSM-0006.

## Security considerations
This ticket is substantially a security deliverable. Any critical vulnerability in an
authentication, payment or file-upload path is escalated to QA-02 and FSM-0009 immediately
rather than waiting for the consolidated report.

## Tenant isolation considerations
Flag any dependency involved in request routing, session handling or database connection
pooling where a vulnerability could cross tenant boundaries.

## Observability requirements
Recommend the dependency scanning cadence and CI integration for FSM-0010.

## Migration requirements
None.

## Rollback considerations
Documentation only. No lockfile change.

## Non-goals
Not upgrading anything. Not fixing vulnerabilities. Not changing the lockfile. Sprint 1 owns
remediation.

## Required review
DO-02 implements · DO-01 peer reviews · TL-01 approves the remediation priority order.

## Required QA
QA-02 verifies the vulnerability register is reproducible and confirms exploitability
assessments are reasoned rather than copied from scanner output.

## Completion procedure
Merge → escalate critical findings to FSM-0009 → feed remediation plan into Sprint 1 →
update `PROJECT_STATE.md` §5.
