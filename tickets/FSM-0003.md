## Objective
Produce a complete inventory of every backend route, handler and service at the baseline
commit, and classify each KEEP / REFACTOR / REPLACE / REMOVE against the V2 architecture.

## Product context
The baseline contains 26 route groups and 48 service files built under a product boundary
that has since been retired. Some of that work is production-quality and must be preserved;
some was scoped to a deliberately thin V1 and cannot carry V2's depth. Master directive §1
is explicit: existing code is not correct merely because it exists.

## User story
As the Technical Lead planning Sprints 2–5, I need to know exactly which backend surfaces
survive, which need rework and which must be replaced, so sprint scope reflects real
starting position rather than assumption.

## Scope
Every route group under `apps/api/src/routes/`. Every service under
`apps/api/src/services/`. Every shared library under `apps/api/src/lib/`. Auth middleware
and Fastify plugins.

Excluded: workers (FSM-0006), schema (FSM-0004), frontend (FSM-0005).

## Deliverables
1. `docs/audit/BACKEND-INVENTORY.md` containing, per route group: route paths and verbs,
   auth requirement, backing service, tenant scoping status, Zod validation status, test
   coverage status, activity events emitted, classification, and one-line rationale.
2. Per-service table: file, domain, exported functions, LOC, dependencies, test file presence, classification.
3. Architectural violation register: business logic in handlers, direct DB access in
   handlers, missing tenant scope, missing Zod validation, `process.env` outside
   `@fsm/config`, `any` usage, hard deletes, missing activity events, float money handling.
4. Domain coverage map: which of the master directive §62 core entities have backend support today.
5. Relocation of `apps/api/src/routes/phase2-operations.test.ts` into its proper module (BD-005).

## Classification rubric
- **KEEP** — meets V2 standards, correct domain boundary, tested, tenant-safe. Carry forward unchanged.
- **REFACTOR** — sound domain model and behaviour, but violates a standard or lacks tests. Fix in place.
- **REPLACE** — behaviour is needed but the implementation cannot carry V2 depth. Rebuild in its sprint.
- **REMOVE** — no longer in scope, superseded, or dead. Delete.

Every classification requires a written rationale. "Looks fine" is not a rationale.

## Acceptance criteria
- [ ] All 26 route groups classified with rationale
- [ ] All service files classified with rationale
- [ ] Every route's auth and tenant-scoping status recorded as verified fact, not assumption
- [ ] Every architectural violation carries file path and line reference
- [ ] Domain coverage map complete against master directive §62
- [ ] Each REPLACE item names its target sprint
- [ ] Each REFACTOR item carries an estimated size (S/M/L)
- [ ] BD-005 resolved and the convention documented
- [ ] No behaviour changed other than the BD-005 file move

## Required tests
Existing suite must pass identically before and after the BD-005 move. No new tests in this
ticket — coverage gaps are findings for FSM-0007.

## Impact
**API:** inventory only; no contract changes. **Database:** none. **Frontend:** none.
**Mobile:** none. **Integration:** integration touchpoints recorded and cross-referenced to FSM-0006.

## Security considerations
Any route found without authentication, without tenant scoping, or trusting a tenant ID from
a request body is escalated immediately to QA-02 and FSM-0009 rather than waiting for the
consolidated report.

## Tenant isolation considerations
Tenant scoping status is a required column, verified by reading the query, not by trusting
the function name.

## Observability requirements
Record which routes currently emit structured logs and correlation IDs; feed gaps into Sprint 1.

## Migration requirements
None.

## Rollback considerations
Documentation plus one file move. Trivially revertible.

## Non-goals
Not refactoring. Not adding tests. Not fixing violations. This ticket produces the decision
record that later sprints execute against.

## Required review
BE-01 implements · BE-02 peer reviews classifications · TL-01 approves the classification set.

## Required QA
QA-01 spot-checks 20% of classifications against the actual source and confirms the
violation register is reproducible.

## Completion procedure
Merge → feed classifications into FSM-0012 → update `PROJECT_STATE.md` §5 → escalate any
security finding to FSM-0009 immediately.
